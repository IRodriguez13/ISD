Thomas,

I first hit this while running xterm 411 on a hobby Unix-like kernel I am
developing (IR0): twm desktop session, serial log showed userspace SIGSEGV in
xterm with rip in strcmp and ret in MapSelections (button.c). Symbolization
pointed at isSELECT(params[j]) with CR2 around 0x9 — a non-NULL garbage String
pointer, not a kernel uaccess fault.

Before sending a client-side patch, I reproduced the same bug class on a stock
Linux host (glibc, no IR0 involved): a minimal program using vanilla
MapSelections/isSELECT logic with param=(char*)9 faults in strcmp the same way
(see attached linux-baseline-repro.c). That convinced me the gap is in xterm's
parameter handling, not my kernel.

In the integrated session the crash occurs in MapSelections() when handling Xt
action parameters for selection/paste (SELECT token in translations):

  rip  → strcmp (first argument dereference)
  ret  → MapSelections (button.c), after isSELECT(params[j])
  CR2  → 0x9 (non-NULL garbage String pointer)

The vanilla loop calls isSELECT(params[j]), which expands to
strcmp(NonNull(value), "SELECT"). NonNull(NULL) is safe, but a non-null
invalid pointer is not rejected and faults inside strcmp.

Attached patch adds InvalidSelectionParam() to skip parameters whose address
is below 4096, logging xtermWarning instead of crashing. We kept the 4096
threshold as a cheap guard against small integer/garbage pointers on x86; happy
to adjust if you prefer a different check.

Verification on our side:

  - patch applies cleanly to vanilla xterm-411/button.c
  - xterm rebuild + desktop session smoke (no crash with patch)
  - linux-baseline-repro.c SIGSEGV on stock Linux without the guard

Please let me know if you want the full serial log / gdb backtrace from the
integrated twm session.
